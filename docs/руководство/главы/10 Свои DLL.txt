# Свои DLL
DLL — библиотека, которую программа загружает при запуске и из которой берёт функции. Сама Windows почти целиком состоит из DLL: `kernel32.dll`, `user32.dll`, `gdi32.dll` и сотни других. Свою DLL делают, когда одни и те же функции нужны нескольким программам, когда часть программы хочется менять, не пересобирая остальное, или когда функции на Си надо отдать программе на другом языке. Эта глава показывает, как WinCC собирает DLL, как программа её подключает, где DLL ищется при сборке и при запуске и что делает функция `DllMain`.

## Как устроена DLL

Снаружи DLL похожа на `.exe`: тот же формат файла, тот же машинный код. Разница в двух вещах. У DLL нет своей точки входа вроде `main` — она ничего не делает сама, пока её функции не позовут. И у неё есть таблица экспорта: список имён функций, которые она отдаёт наружу, с их адресами внутри файла.

Программа, которая берёт функции из DLL, хранит у себя таблицу импорта: какие имена из какой DLL ей нужны. При запуске Windows загружает в память каждую DLL из этого списка, находит в её таблице экспорта нужные имена и вписывает их адреса в программу. Если DLL не нашлась или в ней нет нужного имени, программа не запускается вовсе — Windows показывает сообщение и не выполняет ни одной её строки.

Код DLL в программу не копируется: в `.exe` записано только имя DLL и имена функций. Поэтому DLL можно исправить и пересобрать, и все программы, которые её зовут, получат новые функции без пересборки — лишь бы имена и параметры остались прежними.

## Первая DLL

Пример лежит в папке `examples\dll` вместе с WinCC: библиотека `mathlib` из четырёх функций и программа, которая их зовёт.

```
// файл: mathlib.c
// Своя DLL на WinCC: функции с __declspec(dllexport) видны другим программам.
// сборка: wcc --dll mathlib.c
#include <windows.h>
#include <stdio.h>

static int g_calls;                 // свои данные DLL: у каждого процесса — свои

__declspec(dllexport) int add(int a, int b)
{
    g_calls++;
    return a + b;
}

__declspec(dllexport) double average(const double *v, int n)
{
    g_calls++;
    double s = 0;
    for (int i = 0; i < n; i++)
        s += v[i];
    return n ? s / n : 0;
}

__declspec(dllexport) void greet(const char *name)
{
    g_calls++;
    printf("Привет, %s! (из mathlib.dll)\n", name);
}

__declspec(dllexport) int calls(void)
{
    return g_calls;
}

// Необязательно: Windows зовёт её при загрузке и выгрузке DLL.
BOOL WINAPI DllMain(HINSTANCE dll, DWORD reason, LPVOID reserved)
{
    if (reason == DLL_PROCESS_ATTACH)
        g_calls = 0;
    return TRUE;
}
```

Ключ `--dll` говорит wcc, что нужна библиотека, а не программа. Имя файла по умолчанию — имя первого исходника с расширением `.dll`; другое задаёт `-o`.

```
> wcc --dll mathlib.c
Готово: mathlib.dll — библиотека DLL, 31232 байт, 157 мс
```

`__declspec(dllexport)` — слово Microsoft C, которое WinCC понимает так же: функция попадает в таблицу экспорта. Остальные функции DLL остаются внутренними. Правило выбора такое:

- если хоть у одной функции есть `__declspec(dllexport)`, наружу уходят только такие функции;
- если ни у одной нет, наружу уходят все функции DLL, кроме `static`;
- функции библиотеки Си (`printf`, `malloc` и прочие), попавшие в DLL, наружу не уходят никогда;
- переменные не экспортируются: DLL отдаёт только функции. Если программе нужны данные DLL, их отдают функцией, как `calls` в примере.

Слово можно поставить и у объявления, а не у тела функции: функция, объявленная с `__declspec(dllexport)`, экспортируется, даже если в определении этого слова нет. На этом построен заголовок DLL, о котором ниже.

## Программа, которая зовёт DLL

Программе достаточно объявить функции DLL так же, как они написаны в DLL, и сказать wcc, из какой DLL их брать.

```
// файл: usemath.c
// Программа, которая берёт функции из своей mathlib.dll.
// сборка: wcc usemath.c -l mathlib
#include <stdio.h>

int add(int a, int b);
double average(const double *v, int n);
void greet(const char *name);
int calls(void);

int main(void)
{
    double v[] = { 1.5, 2.5, 3.5, 4.5 };
    greet("мир");
    printf("add(40, 2) = %d\n", add(40, 2));
    printf("average = %.2f\n", average(v, 4));
    printf("вызовов DLL: %d\n", calls());
    return add(2, 2) == 4 ? 0 : 1;
}
```

```
> wcc usemath.c -l mathlib
Готово: usemath.exe — консольная программа, 35328 байт, 109 мс
> usemath
Привет, мир! (из mathlib.dll)
add(40, 2) = 42
average = 3.00
вызовов DLL: 3
```

Ключ `-l mathlib` добавляет `mathlib.dll` к списку DLL, в которых wcc ищет функции, которых нет в самой программе. Имя можно писать с расширением и без, слитно и раздельно: `-l mathlib`, `-lmathlib`, `-l mathlib.dll` — всё одно. Если ключ забыть, wcc перечислит, чего не нашёл:

```
> wcc usemath.c
функции объявлены, но не написаны — greet, add, average, calls: их нет ни в программе, ни в библиотеках Windows (своя DLL — ключ -l имя или #pragma comment(lib, "имя"))
```

У этого сообщения нет файла и строки: объявления верны, не хватает тел функций, а их wcc ищет уже после разбора всех исходников. Если ненайденная функция одна, сообщение начинается словами «функция объявлена, но не написана». А если DLL с таким именем нет ни рядом, ни в системе, wcc скажет и об этом:

```
> wcc usemath.c -l nosuchlib
функции объявлены, но не написаны — greet, add, average, calls: их нет ни в программе, ни в библиотеках Windows (своя DLL — ключ -l имя или #pragma comment(lib, "имя"))
wcc: не найдены библиотеки: nosuchlib.dll
```

Файлов `.lib`, которые просит для DLL компилятор Visual Studio, WinCC не нужно. Он открывает саму `mathlib.dll`, читает её таблицу экспорта и узнаёт оттуда, какие имена она даёт. Поэтому DLL должна существовать к моменту сборки программы: сначала собирается DLL, потом программа.

В окне WinCC DLL собирается видом программы «DLL» (глава 3). Запустить DLL нельзя — запускают программу, которая её зовёт.

## Где ищется DLL

Искать DLL приходится дважды: wcc ищет её при сборке, чтобы прочесть таблицу экспорта, а Windows — при запуске, чтобы загрузить.

:= Когда | Кто ищет | Где, по порядку
: сборка | wcc | папка первого исходника; папка, куда пишется программа (`-o`); системная папка `System32`
: запуск | Windows | папка самой программы; системные папки Windows; текущая папка; папки из переменной `PATH`

Правило на каждый день вытекает из таблицы: DLL лежит в одной папке с программой. Тогда её найдут и wcc при сборке, и Windows при запуске, откуда бы программу ни запустили. Если программа уходит на другой компьютер, DLL едет вместе с ней, в ту же папку.

Имя DLL записывается в программу таким, каким было при сборке. Переименованную DLL программа не найдёт. Если из DLL убрать функцию, которую программа зовёт, программа тоже не запустится: Windows сообщит, что не нашла в библиотеке точку входа с этим именем.

## Заголовок DLL

Объявлять функции DLL в каждой программе заново — путь к ошибке: стоит поменять параметр в DLL и забыть поменять объявление, и программа будет передавать не то. Объявления выносят в заголовок, который подключают и сама DLL, и программы. Тогда компилятор сам сверит объявления с определениями в DLL.

Заголовок может сделать и вторую работу — сказать wcc, из какой DLL брать функции, строкой `#pragma comment(lib, "имя")`. Тогда ключ `-l` не нужен: подключил заголовок — подключил DLL. Но внутри самой DLL эта строка лишняя, а слово `__declspec(dllexport)` нужно только ей. Развести эти случаи помогает макрос, который DLL определяет до подключения заголовка.

```
// файл: textkit.h
// textkit.h — что умеет textkit.dll; подключают и сама DLL, и программы
#pragma once
#ifdef TEXTKIT_BUILD
#define TEXTKIT_API __declspec(dllexport)      // собирается сама DLL: отдать наружу
#else
#define TEXTKIT_API
#pragma comment(lib, "textkit")                // собирается программа: брать из textkit.dll
#endif

TEXTKIT_API int tk_letters(const char *utf8);  // сколько знаков (не байтов) в строке
TEXTKIT_API char *tk_upper(const char *utf8);  // новая строка заглавными; отдать в tk_free
TEXTKIT_API void tk_free(void *p);
```

```
// файл: textkit.c
// сборка: wcc --dll textkit.c
#define TEXTKIT_BUILD
#include "textkit.h"
#include <windows.h>
#include <stdlib.h>

int tk_letters(const char *s)
{
    int n = 0;
    for (; *s; s++)
        if ((*s & 0xC0) != 0x80)        // байты-продолжения буквы не считаются
            n++;
    return n;
}

char *tk_upper(const char *s)
{
    int n = MultiByteToWideChar(CP_UTF8, 0, s, -1, NULL, 0);
    wchar_t *w = malloc(n * sizeof(wchar_t));
    MultiByteToWideChar(CP_UTF8, 0, s, -1, w, n);
    CharUpperW(w);                      // заглавные по правилам Windows, кириллица тоже
    int k = WideCharToMultiByte(CP_UTF8, 0, w, -1, NULL, 0, NULL, NULL);
    char *out = malloc(k);
    WideCharToMultiByte(CP_UTF8, 0, w, -1, out, k, NULL, NULL);
    free(w);
    return out;
}

void tk_free(void *p)
{
    free(p);
}
```

```
// файл: shout.c
// сборка: wcc shout.c
#include <stdio.h>
#include <string.h>
#include "textkit.h"

int main(int argc, char **argv)
{
    const char *text = argc > 1 ? argv[1] : "Съешь же ещё этих мягких французских булок";
    char *up = tk_upper(text);
    printf("%s\n", up);
    printf("знаков: %d, байт: %d\n", tk_letters(text), (int)strlen(text));
    tk_free(up);                        // память выделила DLL — ей и освобождать
    return 0;
}
```

```
> wcc --dll textkit.c
Готово: textkit.dll — библиотека DLL, 24576 байт, 125 мс
> wcc shout.c
Готово: shout.exe — консольная программа, 35328 байт, 109 мс
> shout
СЪЕШЬ ЖЕ ЕЩЁ ЭТИХ МЯГКИХ ФРАНЦУЗСКИХ БУЛОК
знаков: 42, байт: 78
```

Программа собралась без `-l`: строку `#pragma comment(lib, "textkit")` wcc увидел в заголовке. А DLL получила `__declspec(dllexport)` у трёх объявлений и отдала наружу ровно три функции. Заметно и то, что `textkit.dll` вдвое меньше `mathlib.dll`: она не зовёт `printf`, и из библиотеки Си в неё попало совсем немного.

## У DLL своя библиотека Си

Каждая программа WinCC несёт библиотеку Си внутри себя — и каждая DLL тоже. `mathlib.dll` весит 56 КБ как раз поэтому: в ней свой `printf`. Отсюда следует правило, которое касается DLL любого компилятора, у которого библиотека Си своя в каждом модуле: у программы и у DLL разные кучи памяти, разные таблицы открытых файлов, разные `errno`.

- Память, выделенную `malloc` в DLL, освобождает DLL. Поэтому в `textkit` есть `tk_free`: программа отдаёт строку обратно в DLL, и та зовёт свой `free`. Свой `free` программы на чужом указателе испортит её кучу.
- `FILE *`, открытый в программе, нельзя передать в DLL для `fprintf`, и наоборот. Передают имя файла, буфер с данными или описатель Windows (`HANDLE`) — он общий для всего процесса.
- Печатать DLL может: её `printf` пишет в ту же консоль, что и программа, и строки выходят по порядку.

Описатели Windows — окна, файлы `CreateFileA`, события, потоки — принадлежат процессу целиком, и их можно свободно передавать между программой и DLL.

## DllMain

`DllMain` — необязательная функция, которую Windows зовёт, когда DLL загружают в процесс, когда процесс создаёт и завершает потоки и когда DLL выгружают. В WinCC до неё сначала доходит своя точка входа библиотеки: она готовит кучу и библиотеку Си DLL, а потом передаёт вызов в `DllMain`, если такая функция есть.

:= Причина в reason | Когда
: `DLL_PROCESS_ATTACH` | DLL загружена в процесс — при запуске программы или по `LoadLibraryA`
: `DLL_THREAD_ATTACH` | процесс создал новый поток
: `DLL_THREAD_DETACH` | поток завершается
: `DLL_PROCESS_DETACH` | DLL выгружается — программа закончилась или позвала `FreeLibrary`

Если на `DLL_PROCESS_ATTACH` вернуть `FALSE`, Windows сочтёт, что DLL не готова: программа, которая её импортирует, не запустится, а `LoadLibraryA` вернёт `NULL`. Так DLL может отказаться работать, если ей чего-то не хватает.

Пример — DLL, которая докладывает о своей жизни и считает потоки процесса.

```
// файл: watch.c
// сборка: wcc --dll watch.c
// DLL, которая видит, как её загружают, выгружают и как рождаются потоки
#include <windows.h>
#include <stdio.h>

static int g_threads;

BOOL WINAPI DllMain(HINSTANCE dll, DWORD reason, LPVOID reserved)
{
    switch (reason) {
    case DLL_PROCESS_ATTACH:
        printf("[watch] загружена\n");
        break;
    case DLL_THREAD_ATTACH:
        g_threads++;
        break;
    case DLL_PROCESS_DETACH:
        printf("[watch] выгружена, новых потоков было: %d\n", g_threads);
        break;
    }
    return TRUE;
}

__declspec(dllexport) int watch_threads(void)
{
    return g_threads;
}
```

```
// файл: threads.c
// сборка: wcc threads.c -l watch
#include <windows.h>
#include <stdio.h>

int watch_threads(void);

static DWORD WINAPI work(LPVOID arg)
{
    Sleep(50);
    return 0;
}

int main(void)
{
    printf("main: начало\n");
    HANDLE t[3];
    for (int i = 0; i < 3; i++)
        t[i] = CreateThread(NULL, 0, work, NULL, 0, NULL);
    WaitForMultipleObjects(3, t, TRUE, INFINITE);
    for (int i = 0; i < 3; i++)
        CloseHandle(t[i]);
    printf("main: DLL насчитала потоков: %d\n", watch_threads());
    return 0;
}
```

```
> threads
[watch] загружена
main: начало
main: DLL насчитала потоков: 3
[watch] выгружена, новых потоков было: 3
```

Порядок строк показывает, как всё происходит. DLL загружена раньше, чем началась `main`: Windows загружает импортируемые DLL до старта программы. Каждый из трёх потоков, родившись, прошёл через `DllMain` с `DLL_THREAD_ATTACH`. А после возврата из `main` процесс завершается, и DLL получает `DLL_PROCESS_DETACH` — её библиотека после этого сама допишет на диск всё, что DLL не успела.

! Пока работает `DllMain`, Windows держит общую блокировку загрузчика. Внутри неё нельзя ждать другие потоки, загружать другие DLL через `LoadLibraryA` и делать что-то долгое — процесс может намертво зависнуть. Задача `DllMain` — расставить начальные значения; всё большее делают отдельной функцией DLL, которую программа позовёт сама.

## DLL для других языков

DLL, собранная WinCC, — обычная 64-разрядная DLL Windows с именами функций Си без украшений и стандартным для x64 соглашением о вызове. Её может позвать любой язык, который умеет звать функции Си из DLL. Например, программа на C# объявляет функции `mathlib.dll` так:

```
using System.Runtime.InteropServices;

static class MathLib
{
    [DllImport("mathlib.dll")] public static extern int add(int a, int b);
    [DllImport("mathlib.dll")] public static extern double average(double[] v, int n);
}
```

и `MathLib.add(40, 2)` возвращает 42. Типы надо сопоставлять точно: `int` Си — это `int` C#, `double` — `double`, указатель на массив — массив, строка UTF-8 — массив байтов или `string` с указанием кодировки.

Компилятор Visual Studio ждёт к DLL файл `.lib`, а WinCC его не делает. Программе на Visual C такую DLL проще всего подключить через `LoadLibraryA` и `GetProcAddress` — о них глава 11.

## Итог

DLL собирается ключом `--dll`. Наружу уходят функции с `__declspec(dllexport)`, а если таких нет — все функции, кроме `static`; переменные не экспортируются. Программа подключает DLL ключом `-l имя` или строкой `#pragma comment(lib, "имя")`, лучше всего — в заголовке DLL, который подключают обе стороны. wcc читает таблицу экспорта самой DLL, поэтому DLL собирают первой и кладут рядом с исходником программы; при запуске Windows ищет её прежде всего в папке программы.

У DLL своя библиотека Си: память, выделенную в DLL, освобождает DLL, а `FILE *` между модулями не передают. `DllMain` необязательна; она узнаёт о загрузке, выгрузке и потоках и должна работать коротко.
