# Приложение Б. Сообщения компилятора и что с ними делать
Все сообщения `wcc` по-русски. Приложение начинается с того, как их читать, и с разбора самых частых случаев на настоящих примерах. Затем идут таблицы всех сообщений по группам: чтение текста, препроцессор, разбор языка, структурные исключения, типы и выражения, сборка и импорт DLL, ассемблер, командная строка. В конце — о предупреждениях и о том, чего `wcc` не сообщает вовсе, о сообщениях окна WinCC и о том, что печатает сама программа, когда её останавливает сбой.

## Как читать сообщение

Почти каждое сообщение имеет вид:

```
файл:строка: текст
```

Файл — тот, в котором замечена ошибка; это может быть и подключённый заголовок. Строка — номер строки в нём, с единицы. Окно WinCC по такой строке открывает файл и ставит курсор на место (глава 3).

Сообщения бывают двух видов. Ошибка останавливает сборку: готового файла не будет, код выхода `wcc` — 1. Предупреждение имеет вид `файл:строка: предупреждение: текст`: сборка идёт дальше, и если ошибок нет, готовый файл появится, а код выхода будет 0. Окно WinCC показывает предупреждения жёлтым.

Три правила помогают найти ошибку быстрее.

Первое: ошибка одна. `wcc` останавливается на первой ошибке и про остальные не знает. После исправления собирают снова; при следующей сборке может появиться следующая ошибка. Предупреждений перед ней может быть несколько.

Второе: строка — место, где ошибку заметили, а не где её сделали. Компилятор читает текст слово за словом, и пропуск обнаруживается, только когда пришло слово, которого не должно быть. Поэтому при пропущенной `;` или `)` сообщение называет следующую строку. Если на указанной строке всё верно, смотрят строку выше.

Третье: текст сообщения говорит, чего ждал компилятор, а не что сделал автор. «ожидалось ';'» значит, что в этом месте подошла бы точка с запятой; настоящая причина может быть и другой — например, лишнее слово, после которого компилятор уже не может продолжить.

Сообщения без файла и строки — «нет функции main (для окон — WinMain)», «функция объявлена, но не написана — …» и редкая ошибка ассемблера, которую нельзя отнести ни к файлу `.asm`, ни к исходнику на Си («ассемблер, строка N текста …»), — появляются на последнем этапе, когда вся программа уже разобрана. Окно WinCC показывает их в списке ошибок с пустыми колонками «Файл» и «Строка».

## Частые случаи

### Пропущенная точка с запятой

```
double average(int a, int b)
{
    double sum = a + b
    return sum / 2;
}
```

```
average.c:4: ожидалось ';'
```

Точка с запятой пропущена в строке 3, сообщение — о строке 4: компилятор понял, что объявление кончилось без `;`, только когда увидел следующее слово. Так же выглядит пропуск после обычного оператора:

```
#include <stdio.h>

void report(int n)
{
    printf("Готово\n")
    printf("Всего: %d\n", n);
}
```

```
report.c:6: ожидалось ';'
```

Что делать: поставить `;` в конце строки, предшествующей названной.

### Незакрытая фигурная скобка

```
#include <stdio.h>

void table(int n)
{
    for (int i = 1; i <= n; i++) {
        printf("%d x %d = %d\n", i, i, i * i);

}
```

```
table.c:5: не хватает '}': блок, который начинается здесь, не закрыт до конца файла
```

Компилятор доходит до конца файла внутри функции и называет строку, с которой начинается незакрытый блок, — первую строку внутри него. Здесь `}` в строке 8 закрыла цикл, и без пары осталась `{` самой функции `table`, поэтому названа строка 5 — первая строка её тела. Что делать: найти блок без закрывающей `}` ниже названной строки. Помогают отступы: в окне WinCC после `{` строки сдвигаются вправо, и место, где отступ «не вернулся», обычно видно сразу.

Обратный случай — лишняя `}`:

```
int twice(int x)
{
    return x * 2;
}
}
```

```
twice.c:5: лишняя '}': ей нет пары '{'
```

Здесь названа строка самой лишней скобки. Что делать: убрать её или найти `{`, которую забыли написать выше.

### Функция без заголовка

```
void greet(const char *name)
{
    printf("Привет, %s!\n", name);
}
```

```
greet.c:3: функция printf не объявлена (нет #include с ней?)
```

WinCC требует, чтобы функция была объявлена до вызова, как велит стандарт C99. `printf` объявлена в `stdio.h`, а `#include <stdio.h>` здесь забыт. Что делать: подключить нужный заголовок или, для своей функции, написать её объявление (прототип) выше места вызова или в общем заголовке.

### Опечатка в имени

```
int count_spaces(const char *s)
{
    int count = 0;
    for (; *s; s++)
        if (*s == ' ')
            cuont++;
    return count;
}
```

```
count.c:6: неизвестное имя cuont
```

Сообщение называет имя, которого компилятор не знает. Что делать: исправить опечатку или объявить переменную. «неизвестное имя» означает переменную, которой нет; для функции было бы «функция … не объявлена».

### Кавычки из текстового редактора

```
#include <stdio.h>

void hello(void)
{
    printf(“Привет”);
}
```

```
quotes.c:5: неизвестное имя “Привет”
```

Текст, скопированный из Word, из письма или со страницы сайта, часто несёт типографские кавычки `“ ”` или «ёлочки» вместо прямых `"`. Для Си это не кавычки, а буквы, и `“Привет”` читается как одно длинное имя — его сообщение и показывает. Что делать: заменить кавычки на прямые. То же бывает с длинным тире вместо минуса.

### Обратная косая в пути

```
#include <stdio.h>

FILE *open_letter(void)
{
    return fopen("Папка\письмо.txt", "r");
}
```

```
letter.c:5: предупреждение: неизвестная последовательность \п в строке: обратная косая пропущена (в пути пишут \\)
```

В строке Си обратная косая начинает особый знак: `\n` — перевод строки, `\t` — табуляция. Сочетания `\п` в языке нет, поэтому `wcc` предупреждает и поступает так же, как Visual Studio: обратная косая выпадает, буква остаётся. Программа соберётся, но будет открывать файл `Папкаписьмо.txt`. Что делать: в путях писать двойную косую (`"Папка\\письмо.txt"`) или прямую (`"Папка/письмо.txt"`) — Windows понимает обе. Знакомые последовательности предупреждения не дают: `"C:\new"` молча превратится в `C:`, перевод строки и `ew`, поэтому двойная косая в путях нужна всегда.

### Забытый файл программы

```
wcc main.c -o journal.exe
функции объявлены, но не написаны — average, maximum, twice: их нет ни в программе, ни в библиотеках Windows (своя DLL — ключ -l имя или #pragma comment(lib, "имя"); своя библиотека — её файл .lib в команде)
```

Функции объявлены (заголовок подключён), но их тел `wcc` не видел: файлы `stats.c` и `twice.asm` не названы в команде. Подсказка в скобках про `-l` относится к другому случаю — функциям из DLL. Что делать: если функции свои — добавить их файлы в команду (`wcc main.c stats.c twice.asm`); если это функции DLL Windows, которой нет среди всегда просматриваемых, — назвать её ключом `-l` или строкой `#pragma comment(lib, "имя")` (глава 11); если это опечатка в имени функции, объявленной вручную, — исправить её. Для одной функции сообщение звучит так: «функция объявлена, но не написана — имя: её нет …». В окне WinCC оно появляется и тогда, когда программа из нескольких файлов собирается кнопкой «Собрать»: окно собирает только текущий файл.

### Нет функции main

```
int square(int x)
{
    return x * x;
}
```

```
нет функции main (для окон — WinMain)
```

В программе нет функции входа. Так бывает, когда собирают вспомогательный файл отдельно от главного, когда имя написано неверно (`Main`, `mian`) и когда DLL собирают без ключа `--dll`. Что делать: собрать вместе с файлом, где есть `main`, исправить имя или добавить `--dll`.

### Одно имя у переменной и функции

```
int x;

int x(void)
{
    return 1;
}
```

```
names.c:3: имя x уже занято переменной
```

Глобальная переменная и функция живут в одном пространстве имён, и два разных предмета с одним именем быть не могут. Если функция объявлена раньше переменной, сообщение будет обратным — «имя x уже занято функцией». Что делать: переименовать одно из двух.

### Массив переменной длины с начальным значением

```
void fill(int n)
{
    int buffer[n] = { 0 };
    for (int i = 0; i < n; i++)
        buffer[i] = i;
}
```

```
vla.c:3: массив переменной длины нельзя инициализировать
```

Массив, размер которого становится известен только при выполнении (`int buffer[n]`), WinCC заводит в стеке функции, но начального значения `= { … }` у него быть не может — так велит стандарт. Что делать: убрать инициализатор и заполнить массив циклом или `memset(buffer, 0, sizeof buffer)` — `sizeof` у такого массива считается при выполнении. Так же нельзя сделать такой массив `static` или `extern`, завести его вне функции или полем структуры — эти сообщения есть в таблице «Разбор языка».

### Код исключения вне __except

```
#include <windows.h>
#include <stdio.h>

int divide(int a, int b)
{
    int r = 0;
    __try {
        r = a / b;
    } __except (EXCEPTION_EXECUTE_HANDLER) {
        printf("сбой\n");
    }
    printf("код %lx\n", GetExceptionCode());
    return r;
}
```

```
seh.c:12: GetExceptionCode() бывает только в __except: в условии или в блоке
```

Код исключения существует, только пока исключение обрабатывается: в условии `__except (…)` и внутри его блока. После блока его уже нет. Что делать: запомнить код там, где он есть, — завести `DWORD code = 0;` до `__try` и в блоке `__except` написать `code = GetExceptionCode();`. Другие сообщения о `__try`, `__except`, `__finally` и `__leave` — в таблице «Структурные исключения».

### Незнакомая #pragma

```
#pragma once
#pragma hdrstop
int value = 1;
```

```
pch.c:2: предупреждение: неизвестная #pragma hdrstop — пропущена
```

Это предупреждение, а не ошибка: сборка идёт дальше, строка пропускается. Чаще всего такая `#pragma` написана для другого компилятора и WinCC не нужна. Что делать: если строка действительно не нужна — ничего или убрать её; если файл общий с другим компилятором — взять её в `#ifndef __WINCC__` … `#endif`. Распространённые чужие `#pragma` (`warning`, `region`, `optimize`, `intrinsic`, `GCC`, `clang`, `omp` и подобные) WinCC пропускает молча, без предупреждения.

### Проверка при сборке: _Static_assert

```
_Static_assert(sizeof(long) == 8, "long не 8 байт");
```

```
size.c:1: условие _Static_assert ложно: long не 8 байт
```

`_Static_assert` (и `static_assert`) проверяет условие во время сборки: если оно ложно, сборка останавливается с текстом, который дал автор. Здесь условие ложно, потому что в Windows `long` — 4 байта. Что делать: если проверка верна, а программа рассчитана на другую систему, — поправить программу (здесь взять `long long`); если ошибочна сама проверка — исправить условие.

### Незакрытое условие препроцессора

```
#ifdef DEBUG
#define LOG(x) printf("%s\n", x)
#else
#define LOG(x)
```

```
debug.c:1: #if не закрыт #endif
```

Строка в сообщении — та, где условие открыто. Что делать: добавить `#endif` в нужном месте.

### Директива #error

```
#ifndef _WIN64
#error нужна 64-битная Windows
#endif
#ifdef __WINCC__
#error этот файл не для WinCC
#endif
int value = 1;
```

```
ver.c:5: #error этот файл не для WinCC
```

Сработала директива `#error` — автор файла сам запретил его собирать при этом условии. Что делать: выяснить, почему условие сработало (часто это значит, что файл рассчитан на другой компилятор или нужен ключ `-D`). Похожая директива `#warning` не останавливает сборку, а печатает предупреждение: `#warning осторожно` даёт строку `файл:строка: предупреждение: осторожно`.

### Ошибка во вставке на ассемблере

```
long long fast_double(long long x)
{
    asm("movq rax, 1");
    return x * 2;
}
```

```
fast.c:3: ассемблер: movd/movq: нужен регистр xmm [movq rax, 1]
```

Ошибка во вставке `asm("…")` внутри функции на Си приходит с файлом и строкой исходника, как любая другая. В квадратных скобках — сама строка ассемблера, на которой ассемблер споткнулся. Подробно об ошибках ассемблера — в разделе «Ассемблер» ниже.

## Чтение текста

Ошибки и предупреждения, найденные при разбиении текста на слова, числа и строки.

:= Сообщение | Когда бывает | Что делать
: строка не закрыта | у строки в `"…"` нет закрывающей кавычки до конца строки файла | закрыть кавычку; длинную строку переносить как `"…" "…"` или через `\` в конце строки
: символ не закрыт | у символа в `'…'` нет закрывающей кавычки или в нём пусто | закрыть кавычку; для строки — двойные кавычки
: в символьной константе больше 4 знаков | в `'…'` больше четырёх знаков: `'ABCDE'`; константа из нескольких знаков (`'RIFF'`) — это число `int` из их байтов, а в `int` их помещается четыре | не больше четырёх знаков; для текста — строка в двойных кавычках
: комментарий не закрыт | у `/*` нет `*/` до конца файла | закрыть комментарий
: неверная шестнадцатеричная последовательность | после `\x` в строке или символе нет шестнадцатеричной цифры | `\x41`, `\xD0`
: после \u нужно 4 шестнадцатеричных цифр | неполная запись `\u` | `\u0416`; для символа за U+FFFF — `\U0001F600`
: после \U нужно 8 шестнадцатеричных цифр | неполная запись `\U` | восемь цифр, например `\U0001F600`
: \uD800: такого символа в Юникоде нет | код из области суррогатов или больше U+10FFFF | записать символ как есть или верным кодом
: в u8'' помещается только символ ASCII | в `u8'…'` символ за пределами ASCII | `u8"…"` для строки или `U'…'` для символа
: символ не помещается в char16_t: возьмите U'' | в `u'…'` символ за U+FFFF | `U'…'`
: символ не помещается в wchar_t (16 бит в Windows): возьмите U'' | в `L'…'` символ за U+FFFF (например, эмодзи) | `U'…'` или строка `L"…"` (в строке пара UTF-16 допустима)
: неверное число | число записано неправильно, например `0x` без цифр | исправить запись
: неверная цифра в числе | цифра не той системы: `089` (восьмеричное), `0b2` | убрать ведущий 0 или исправить цифру
: неверная степень в числе | после `e` или `p` нет цифр: `1e+` | `1e+5`
: у шестнадцатеричной дроби нужна степень двойки: p | шестнадцатеричное число с точкой без `p`: `0x1.8` | дописать степень: `0x1.8p0` (это 1,5), `0x1p4` (это 16)
: непонятный знак '…' | в тексте управляющий символ (код меньше 32, кроме пробелов, табуляции и концов строк) | удалить его; обычно попадает при копировании
: предупреждение: неизвестная последовательность \… в строке: обратная косая пропущена (в пути пишут \\) | после `\` в строке буква, которой нет среди последовательностей Си; сборка продолжается, косая выпадает | в путях — `\\` или `/`; см. «Обратная косая в пути»

Буквы за пределами ASCII (кириллица, типографские знаки) `wcc` считает частью имени — поэтому `int счёт = 3;` собирается, а кавычки `“ ”` дают «неизвестное имя». Знаки `@`, `$` и обратная кавычка вне строк сообщения «непонятный знак» не дают: они становятся отдельными словами, и ошибка выходит позже, обычно одним из сообщений «ожидалось …».

Исходник в UTF-8 (с меткой BOM или без), в UTF-16 с меткой BOM и в Windows-1251 читается без ошибок: два последних `wcc` сам переводит в UTF-8.

## Препроцессор

:= Сообщение | Когда бывает | Что делать
: нет файла имя | заголовок не найден ни в одном месте поиска (глава 4) | проверить имя и папку; для своих заголовков — `"…"` и `-I папка`
: после #include нужно имя файла | после `#include` нет ни `"…"`, ни `<…>` | дописать имя
: ожидалось '>' | у `<имя.h` нет `>` до конца строки | закрыть скобку
: макрос в #include должен дать "файл.h" или <файл.h> | после `#include` стоит макрос, а он раскрылся не в имя файла | `#define H <stdio.h>` и затем `#include H`
: макрос в #include дал <… без '>' | макрос раскрылся в `<имя.h` без закрывающей скобки | закрыть скобку в теле макроса
: в __has_include нужно "файл.h" или <файл.h> | в `__has_include(…)` не имя файла | `#if __has_include(<stdio.h>)`
: слишком глубокие #include | больше 32 вложенных включений, обычно заголовок включает сам себя | защитить заголовок `#ifndef`/`#define`/`#endif` или `#pragma once`
: неизвестная директива | после `#` незнакомое слово: `#incldue`, `#defien` | исправить слово
: после #define нужно имя | `#define` без имени или с числом вместо имени | дописать имя
: после #undef нужно имя | то же для `#undef` | дописать имя

Строка в сообщениях о числе аргументов — строка вызова макроса.

`#line N "файл"` меняет счёт: следующая строка считается строкой N этого файла, и сообщения дальше называют уже новые номер и имя. `#pragma message("текст")` печатает этот текст при сборке и сборку не останавливает.

## Структурные исключения

Сообщения о `__try`, `__except`, `__finally` и `__leave` — исключениях в духе Microsoft C (`windows.h`).

:= Сообщение | Когда бывает | Что делать
: после __try нужен блок { } | за `__try` не `{` | `__try { … }`
: блок __try не закрыт | у блока `__try` нет закрывающей `}` до конца файла | дописать `}`
: после __try { } нужен __except (...) { } или __finally { } | за блоком `__try` нет ни `__except`, ни `__finally` | дописать один из них
: после __except (...) нужен блок { } | за условием `__except (…)` не `{` | `__except (EXCEPTION_EXECUTE_HANDLER) { … }`
: после __finally нужен блок { } | за `__finally` не `{` | `__finally { … }`
: условие __except — целое число: EXCEPTION_EXECUTE_HANDLER и подобные | условие `__except (…)` — не целое: указатель, `double`, структура | условие должно давать `EXCEPTION_EXECUTE_HANDLER`, `EXCEPTION_CONTINUE_SEARCH` или `EXCEPTION_CONTINUE_EXECUTION`; свой фильтр — функция, которая возвращает одно из них
: __try внутри __finally и внутри условия __except не поддерживается | `__try` написан в блоке `__finally` или в выражении условия `__except (…)` | вынести этот код в отдельную функцию со своим `__try` и вызвать её
: return внутри __finally не поддерживается | `return` в блоке `__finally` | запомнить значение в переменной и вернуть его после всего `__try … __finally`
: __leave вне блока __try | `__leave` не внутри `__try` | `__leave` выходит из ближайшего `__try`; вне его — `break`, `return` или `goto`
: слишком много вложенных __try | больше 64 блоков `__try … __finally` вложено друг в друга | разнести вложенность по функциям
: в одной функции больше 256 __try | в одной функции больше 256 блоков `__try` | разделить функцию на несколько
: GetExceptionCode() бывает только в __except: в условии или в блоке | код исключения спрошен вне `__except` | см. «Код исключения вне __except»
: GetExceptionInformation() бывает только в условии __except (...) | `GetExceptionInformation()` в блоке `__except` или вне его | вызывать прямо в условии и передавать в функцию-фильтр: `__except (filter(GetExceptionInformation()))`; что нужно дальше — запомнить в фильтре
: AbnormalTermination() бывает только в блоке __finally | `AbnormalTermination()` вне блока `__finally` | спрашивать внутри `__finally`

Коды исключений, `EXCEPTION_POINTERS` и функции вроде `RaiseException` — в приложении В, в разделе о `windows.h` (файл `win\except.h`).

## Ассемблер

Ошибка в ассемблерном тексте выглядит по-разному в зависимости от того, где этот текст написан.

Во вставке `asm("…")` внутри функции на Си ошибка приходит с файлом и строкой исходника, а после слова `ассемблер` — что не так и, в квадратных скобках, сама строка ассемблера (см. «Ошибка во вставке на ассемблере» выше):

```
fast.c:3: ассемблер: movd/movq: нужен регистр xmm [movq rax, 1]
```

В файле `.asm` ошибка приходит с именем этого файла и номером строки в нём, как ошибка в исходнике на Си:

```
bits.asm:7: ассемблер: перед этой строкой нет метки 1: [jmp 1b]
```

Во вставке `asm("…")` вне функций сообщение называет файл и строку Си, где стоит вставка.

Остаётся редкий случай, когда строку нельзя отнести ни к файлу `.asm`, ни к исходнику на Си. Тогда сообщение называет номер строки общего ассемблерного текста всей программы:

```
ассемблер, строка 8709 текста (wcc -S сохранит его в .s): текст ошибки [строка]
```

В квадратных скобках — сама строка с ошибкой; её почти всегда достаточно, чтобы найти место поиском по своим файлам. Если не хватает, собирают ещё раз с ключом `-S` и открывают файл `.s`: на названной строке стоит та же команда, а выше неё — метка ближайшей функции. Окно WinCC показывает такую ошибку в списке без файла и строки.

## Предупреждения и чего wcc не сообщает

Предупреждений у `wcc` три вида: директива `#warning`, незнакомая последовательность с обратной косой в строке и незнакомая `#pragma`. Все они печатаются строкой `файл:строка: предупреждение: текст` в поток ошибок, сборку не останавливают и кода выхода не меняют.

Всё остальное, что разрешено языком, `wcc` собирает молча, даже то, на что другие компиляторы указали бы. Такой фрагмент собирается без единого слова:

```
#include <stdio.h>

int f(void) { }

void dubious(void)
{
    printf("%d\n", "строка");
    int x = "abc";
    char *p = 5;
    int unused;
    unsigned u = -1;
    if (x = 0)
        puts("никогда");
}
```

Здесь функция `f` не возвращает значения, `printf` получает строку вместо числа, целой переменной присвоен адрес строки, указателю — число, переменная `unused` не нужна, а в условии `if` стоит присваивание вместо сравнения. Каждая из этих строк — частая причина неверной работы программы. Что с этим делать: включить в привычку собирать трудный код ещё и другим компилятором с предупреждениями (если он есть под рукой), а в WinCC — проверять результаты печатью, `assert` и `_Static_assert` для того, что известно уже при сборке.

## Когда программа остановилась сама

Если собранная программа делает то, чего процессор сделать не может, библиотека WinCC перехватывает сбой, печатает строку и завершает программу. Код выхода — код сбоя Windows. Перед этим сбой передаётся обработчику сигнала, если программа поставила его функцией `signal` (глава 6); переполнение стека обработчику не передаётся — для него в стеке уже нет места. Сбой внутри `__try` с подходящим `__except` до библиотеки не доходит: она ловит только то, чего не поймал ни один `__try`.

:= Строка | Код выхода | Причина
: программа остановлена: деление на ноль | `C0000094` | целое деление на 0 во время работы
: программа остановлена: переполнение при делении | `C0000095` | деление самого малого `int` на -1
: программа остановлена: обращение к чужой памяти | `C0000005` | запись или чтение по нулевому или неверному указателю, выход за массив далеко за его границы
: программа остановлена: неверная инструкция | `C000001D` | процессор встретил команду, которой не знает; обычно ошибка во вставке на ассемблере
: программа остановлена: переполнение стека (слишком глубокая рекурсия или слишком большой массив внутри функции; больше стека даёт ключ wcc --stack МБ) | `C00000FD` | стек главного потока кончился
: программа остановлена: сбой | код сбоя | другой сбой процессора

Пример — запись по нулевому указателю:

```
#include <stdio.h>

void crash(void)
{
    int *p = NULL;
    printf("Сейчас будет запись по нулевому адресу\n");
    *p = 1;
}
```

Вызов `crash()` из `main` печатает:

```
Сейчас будет запись по нулевому адресу

программа остановлена: обращение к чужой памяти
```

Код выхода программы при этом — `-1073741819`, то есть `C0000005`. Окно консоли, открытое WinCC по F5, покажет его в строке «[Программа завершилась, код -1073741819]».

При переполнении стека код выхода — `-1073741571`, то есть `C00000FD`. Что делать — в главе 4, раздел о ключе `--stack`: дать программе больше стека или большие массивы заводить через `malloc`.

Целое деление на ноль, записанное прямо в тексте (`return 10 / 0;`), `wcc` не считает ошибкой и собирает; программа остановится на этой строке во время работы. Сообщение «деление на ноль» при сборке бывает только там, где значение нужно уже при сборке, — в размере массива, в `case`, в инициализаторе глобальной переменной.
