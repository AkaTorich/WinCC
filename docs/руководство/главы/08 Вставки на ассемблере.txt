# Вставки на ассемблере
Иногда программе нужна команда процессора, которой нет в языке Си: счётчик тактов `rdtsc`, сведения о процессоре `cpuid`, 80-битная арифметика x87. WinCC позволяет вписать такие команды прямо в программу — строкой `asm("…")` внутри функции, функцией без пролога `__declspec(naked)`, целыми функциями вне функций или отдельным файлом `.asm`. Ассемблер у WinCC свой, тот же, что переводит в машинный код всю программу, поэтому вставки не требуют никаких внешних инструментов. Эта глава объясняет, как устроен кадр функции, где лежат аргументы и локальные переменные и как вернуть результат, — без этого вставка работает по случайности. А для самых ходовых команд вставка не нужна вовсе: заголовок `intrin.h` даёт их готовыми, в виде функций.

## Как компилятор видит вставку

WinCC переводит программу на Си в текст на ассемблере x86-64 и затем сам собирает этот текст в машинный код. Строка из `asm("…")` вклеивается в этот текст как есть, на место оператора. Компилятор не разбирает её смысл и не знает, какие регистры она портит. Одно он с ней всё же делает: там, где во вставке стоит `@имя` локальной переменной или параметра функции, он подставляет место этой переменной в кадре функции. В GCC для связи с переменными есть запись с ограничениями (`"=r"(x)` и подобное) — в WinCC её нет, и `@имя` её заменяет. Всё остальное команды вставки находят сами: в регистрах, по известным смещениям в кадре функции, по именам глобальных переменных.

Синтаксис — Intel, как у Microsoft и в документации процессоров: сначала куда, потом откуда (`mov rax, rcx`), размер памяти словами (`dword ptr [rax]`), числа десятичные или с `0x`. Несколько команд в одной строке разделяются `\n`, а соседние строковые литералы Си склеиваются — поэтому вставку удобно писать столбиком, по команде на строку.

Увидеть, во что превратилась программа, можно ключом `-S` (глава 4): рядом с программой ляжет файл `.s` со всем ассемблерным текстом, и в нём видно, куда встала вставка и что вокруг неё.

## Кадр функции

Каждая функция, которую WinCC делает из Си, начинается одинаково:

```
  push rbp
  mov rbp, rsp
  sub rsp, N                        ; место под локальные переменные
  mov qword ptr [rbp+16], rcx       ; первый аргумент
  mov qword ptr [rbp+24], rdx       ; второй
  mov qword ptr [rbp+32], r8        ; третий
  mov qword ptr [rbp+40], r9        ; четвёртый
```

По правилам 64-разрядной Windows первые четыре аргумента приходят в регистрах `rcx`, `rdx`, `r8`, `r9`, а дробные — в `xmm0`…`xmm3`. Вызывающая функция оставляет над адресом возврата 32 байта — «домашние ячейки» для этих четырёх аргументов. WinCC в начале каждой функции переписывает аргументы из регистров в эти ячейки. Пятый и следующие аргументы вызывающий кладёт в стек сразу за ними. Получается простая картина: аргумент номер `k` (с нуля) лежит в `[rbp+16+8*k]`, будь он целым, указателем или `double`.

:= Аргумент | Адрес | Пришёл в регистре
: первый | `[rbp+16]` | `rcx` или `xmm0`
: второй | `[rbp+24]` | `rdx` или `xmm1`
: третий | `[rbp+32]` | `r8` или `xmm2`
: четвёртый | `[rbp+40]` | `r9` или `xmm3`
: пятый, шестой… | `[rbp+48]`, `[rbp+56]`… | в стеке

У целого числа короче восьми байт значимы только младшие байты ячейки: `int` читается как `dword ptr [rbp+16]`. Одно исключение: если функция возвращает большую структуру (больше восьми байт), в первой ячейке лежит адрес, куда эту структуру положить, а аргументы сдвигаются на одну ячейку дальше.

Ответ функция оставляет там же, где его ждёт вызывающий: целое и указатель — в `rax` (`eax` для `int`), дробное — в `xmm0`. Конец функции — метка `.L.return.имя_функции`: на ней стоят команды, которые снимают кадр и возвращаются. Вставка, которая уже положила ответ в `rax`, прыгает туда: `jmp .L.return.ticks`. А после вставки в тексте Си всё равно пишется `return 0;` — без него компилятор не позволит функции, объявленной с результатом, закончиться; до этой строки дело не дойдёт. Есть путь проще: положить ответ в локальную переменную и вернуть её обычным `return` — об этом следующий раздел.

## Локальные переменные и параметры: @имя

Локальные переменные лежат ниже `rbp`, по смещениям, которые компилятор выбирает сам, и заранее их не угадать. Поэтому вставка называет их по имени со знаком `@` впереди: `@x` компилятор заменит местом переменной `x` в кадре, вида `[rbp-24]`. Так же называются параметры функции: `@v` — это место параметра `v`, и считать смещения `[rbp+16]`, `[rbp+24]` самому больше не нужно. Размер, как и у любого обращения к памяти, пишется словами перед именем: `dword ptr @x` для `int`, `qword ptr @x` для `long long` или указателя.

Зачем это нужно: данные идут во вставку и обратно без глобальных переменных и без счёта смещений. Вставка берёт значение из переменной, считает в регистрах и кладёт ответ в другую переменную, а дальше функция продолжается на Си, как ни в чём не бывало. Компилятор WinCC не держит значений в регистрах между операторами Си, поэтому в памяти переменной всегда лежит её текущее значение, а то, что записала вставка, Си увидит в следующей же строке.

```
#include <stdio.h>

// Сколько единичных битов в числе: popcnt считает их одной командой
static int bits_in(unsigned long long v)
{
    long long n;
    asm("popcnt rax, qword ptr @v\n"
        "mov qword ptr @n, rax");
    return (int)n;
}

// Байты числа в обратном порядке: bswap меняет их местами прямо в регистре
static unsigned long long swap_bytes(unsigned long long v)
{
    asm("mov rax, qword ptr @v\n"
        "bswap rax\n"
        "mov qword ptr @v, rax");
    return v;
}

int main(void)
{
    printf("%d %d %d\n", bits_in(0), bits_in(0xF0F0), bits_in(~0ULL));
    printf("%llx\n", swap_bytes(0x1122334455667788ULL));
    return 0;
}
```

```
0 8 64
8877665544332211
```

Здесь не понадобились ни домашние ячейки `[rbp+16]`, ни прыжок к `.L.return`: вставка пишет ответ в переменную, а `return` на Си возвращает его как обычно. Параметр `v` во второй функции служит и входом, и выходом — в его ячейку вставка записала перевёрнутое число.

Несколько правил, которые следуют из того, что подставляет компилятор:

- `@имя` уже содержит квадратные скобки, поэтому пишется без своих: `dword ptr @x`, а не `[@x]`.
- Если переменная — указатель, то `@p` — это место самого указателя. Чтобы добраться до того, на что он указывает, указатель сначала читают в регистр, а потом обращаются через регистр: `mov r8, qword ptr @p` и затем `mov dword ptr [r8], eax`.
- Подстановка работает только во вставке внутри функции: у `asm` вне функций и у файла `.asm` локальных переменных нет.
- Глобальные переменные по-прежнему пишутся через `rip` — следующий раздел.

## Глобальные переменные и регистры

Глобальная переменная доступна вставке по имени, через адрес относительно текущей команды: `[rip+counter]`. Так обращаются к данным все программы x86-64 — код и данные лежат рядом, и адрес не зависит от того, куда Windows загрузила программу. Можно прибавить смещение: `[rip+vendor+4]` — пятый байт массива `vendor`. Если имя переменной совпадает с именем регистра (`dx`, `al`, `cl`), перед ним ставится `@`: `[rip+@dx]` — переменная `dx`, а не регистр. `static` переменные тоже доступны, если их имя в программе одно.

С регистрами правило задаёт сама Windows. Регистры `rax`, `rcx`, `rdx`, `r8`–`r11` и `xmm0`–`xmm5` можно портить свободно: вызывающий от них ничего не ждёт. А `rbx`, `rsi`, `rdi`, `r12`–`r15`, `xmm6`–`xmm15` обязаны пережить вызов: если вставка их меняет, она сохраняет их в стеке (`push rbx` … `pop rbx`) и возвращает. `rbp` и `rsp` трогать нельзя вовсе — на них держится кадр. Компилятор WinCC сам не держит значений в регистрах между операторами Си, так что вставка посреди функции не собьёт её вычисления, если соблюдает эти правила.

## Числовые метки

Все обычные метки ассемблерного текста — общие для всей программы. Если две вставки объявят метку `next`, они помешают друг другу. Для коротких переходов внутри вставки есть числовые метки: `1:`, `2:` и так далее. Переход пишется номером с буквой: `1b` — к ближайшей метке `1:` выше (назад), `1f` — к ближайшей метке `1:` ниже (вперёд). Одну и ту же цифру можно ставить сколько угодно раз — в разных функциях, в разных вставках одной функции, даже в одной вставке, — и каждый переход найдёт свою, ближайшую в нужную сторону.

Вот алгоритм Евклида: пока делитель не ноль, число заменяется делителем, а делитель — остатком. Цикл держится на метке `1:`, выход из него — на `2:`.

```
#include <stdio.h>

// Наибольший общий делитель: div кладёт частное в rax, остаток — в rdx
static unsigned long long gcd(unsigned long long a, unsigned long long b)
{
    asm("mov rax, qword ptr @a\n"
        "mov rcx, qword ptr @b\n"
        "1:\n"
        "test rcx, rcx\n"
        "jz 2f\n"                       // делитель ноль — ответ в rax
        "xor edx, edx\n"
        "div rcx\n"
        "mov rax, rcx\n"
        "mov rcx, rdx\n"
        "jmp 1b\n"                      // снова к началу цикла
        "2:\n"
        "mov qword ptr @a, rax");
    return a;
}

int main(void)
{
    printf("%llu %llu %llu\n", gcd(48, 18), gcd(1071, 462), gcd(17, 5));
    return 0;
}
```

```
6 21 1
```

Числовые метки особенно выручают в макросах: вставка из макроса, вызванного в одной функции дважды, дала бы две одинаковые обычные метки, а с числовыми ей ничего не грозит. Так написан, например, `_BitScanForward` в `intrin.h`.

## Ответ через rax: счётчик тактов

Команда `rdtsc` читает счётчик тактов процессора: 64-битное число, младшая половина которого оказывается в `eax`, а старшая — в `edx`. Вставка склеивает их в `rax` и прыгает к концу функции — так ответ возвращается без всякой переменной.

```
#include <stdio.h>

// Счётчик тактов процессора: rdtsc кладёт младшие 32 бита в eax, старшие — в edx
static unsigned long long ticks(void)
{
    asm("rdtsc\n"
        "shl rdx, 32\n"
        "or rax, rdx\n"
        "jmp .L.return.ticks");
    return 0;
}

static double slow_sum(int n)
{
    double s = 0;
    for (int i = 1; i <= n; i++)
        s += 1.0 / i;
    return s;
}

int main(void)
{
    for (int n = 1000; n <= 1000000; n *= 10) {
        unsigned long long t0 = ticks();
        double s = slow_sum(n);
        unsigned long long t1 = ticks();
        printf("n = %7d: сумма %.6f, %llu тактов, %.1f на шаг\n", n, s, t1 - t0, (double)(t1 - t0) / n);
    }
    return 0;
}
```

```
n =    1000: сумма 7.485471, 20936 тактов, 20.9 на шаг
n =   10000: сумма 9.787606, 209258 тактов, 20.9 на шаг
n =  100000: сумма 12.090146, 2108530 тактов, 21.1 на шаг
n = 1000000: сумма 14.392727, 21155557 тактов, 21.2 на шаг
```

Числа у каждого запуска свои: процессор меняет частоту, Windows переключает задачи. Но порядок виден сразу: около двадцати тактов на шаг цикла, и почти все они уходят на деление дробных чисел — одну из самых долгих команд процессора. Это быстрее и точнее, чем `clock()`, у которого шаг — миллисекунда. Та же функция есть готовой в `intrin.h` под именем `__rdtsc()`.

## Сохранение регистров: cpuid

Команда `cpuid` рассказывает о процессоре: с `eax = 0` она возвращает имя производителя — двенадцать букв в `ebx`, `edx` и `ecx`, с `eax = 1` — биты возможностей. Она пишет в `rbx`, а его вызывающий ждёт нетронутым, поэтому вставка начинается с `push rbx` и кончается `pop rbx`. Результат кладётся в глобальные переменные — функции ничего возвращать не нужно, и `jmp` к концу не требуется: после вставки функция просто кончается.

```
#include <stdio.h>

static char vendor[13];
static unsigned int features;

static void cpu_info(void)
{
    asm("push rbx\n"                        // cpuid портит rbx, а его надо сохранить
        "xor eax, eax\n"
        "cpuid\n"
        "mov dword ptr [rip+vendor], ebx\n"
        "mov dword ptr [rip+vendor+4], edx\n"
        "mov dword ptr [rip+vendor+8], ecx\n"
        "mov eax, 1\n"
        "cpuid\n"
        "mov dword ptr [rip+features], ecx\n"
        "pop rbx");
}

int main(void)
{
    cpu_info();
    printf("производитель: %s\n", vendor);
    printf("SSE4.2: %s, POPCNT: %s, AVX: %s\n",
           features & (1u << 20) ? "есть" : "нет",
           features & (1u << 23) ? "есть" : "нет",
           features & (1u << 28) ? "есть" : "нет");
    return 0;
}
```

```
производитель: GenuineIntel
SSE4.2: есть, POPCNT: есть, AVX: есть
```

Такую проверку ставят перед тем, как пользоваться командами, которые есть не у всех процессоров.

## Функция без пролога: naked

Кадр, который строит компилятор, удобен для вставки посреди кода на Си, но для функции, написанной целиком на ассемблере, он лишний: аргументы и так лежат в регистрах, а прыжок к `.L.return` — лишний шаг. `__declspec(naked)` перед функцией велит компилятору не писать ни пролога, ни эпилога. Тело такой функции — только `asm(…)`: аргументы берутся прямо из `rcx`, `rdx`, `r8`, `r9`, ответ кладётся в `rax`, выход — своей командой `ret`. Строки `return` после вставки не нужно. Зато функция остаётся обычной функцией Си: у неё есть прототип с типами, и вызывать её можно, ничего больше не объявляя.

```
#include <stdio.h>

// Без пролога и эпилога: аргументы — в ecx, edx, r8d, выход — своим ret
__declspec(naked) int clamp(int v, int lo, int hi)
{
    asm("mov eax, ecx\n"
        "cmp eax, edx\n"
        "cmovl eax, edx\n"              // меньше нижней границы — берём её
        "cmp eax, r8d\n"
        "cmovg eax, r8d\n"              // больше верхней — берём верхнюю
        "ret");
}

int main(void)
{
    printf("%d %d %d\n", clamp(-5, 0, 100), clamp(50, 0, 100), clamp(500, 0, 100));
    return 0;
}
```

```
0 50 100
```

Раз кадра нет, нет и домашних ячеек `[rbp+16]` и метки `.L.return.имя`: всё, что было сказано о них выше, относится к обычным функциям. Регистры, которые Windows велит сохранять, функция без пролога сохраняет сама, как и любая вставка.

## Функции целиком на ассемблере

`asm("…")` можно написать и вне функций — тогда текст встаёт в программу отдельно, и в нём можно определить целую функцию: метка с её именем, команды, `ret`. Здесь нет кадра, который строит компилятор, поэтому аргументы берутся прямо из регистров `rcx`, `rdx`, `r8`, `r9`, а ответ кладётся в `rax`. Чтобы функцию можно было вызвать из Си, её объявляют прототипом. Так удобно держать несколько функций в одном куске текста — ниже та же `clamp` и счёт единичных битов.

```
#include <stdio.h>

// Целые функции на ассемблере — вне функций Си. Аргументы приходят
// в rcx, rdx, r8, r9, ответ — в rax; кадра нет, только ret.
asm(".text\n"
    "clamp:\n"                          // int clamp(int v, int lo, int hi)
    "  mov eax, ecx\n"
    "  cmp eax, edx\n"
    "  cmovl eax, edx\n"
    "  cmp eax, r8d\n"
    "  cmovg eax, r8d\n"
    "  ret\n"
    "bit_count:\n"                      // int bit_count(unsigned long long v)
    "  xor eax, eax\n"
    ".Lbit_count.next:\n"
    "  test rcx, rcx\n"
    "  jz .Lbit_count.done\n"
    "  lea rdx, [rcx-1]\n"
    "  and rcx, rdx\n"                  // гасит младшую единицу
    "  inc eax\n"
    "  jmp .Lbit_count.next\n"
    ".Lbit_count.done:\n"
    "  ret\n");

int clamp(int v, int lo, int hi);
int bit_count(unsigned long long v);

int main(void)
{
    printf("%d %d %d\n", clamp(-5, 0, 100), clamp(50, 0, 100), clamp(500, 0, 100));
    printf("%d %d\n", bit_count(255), bit_count(0x8000000000000001ULL));
    return 0;
}
```

```
0 50 100
8 2
```

Перед текстом стоит `.text` — указание, что дальше идёт код, а не данные. Метки внутри функции начинаются с `.L` и несут её имя: все обычные метки ассемблерного текста программы — общие, и две функции с меткой `next` помешали бы друг другу. Для коротких циклов вместо них годятся и числовые метки `1:` с переходами `1b` и `1f` — они не мешают друг другу нигде.

## Файлы .asm

Длинный код на ассемблере удобнее держать отдельным файлом. wcc принимает файлы `.asm` в той же командной строке, что и исходники на Си: `wcc main.c bits.asm -o bits.exe`. В окне WinCC файл `.asm` открывается и правится как любой другой, а собирается вместе с `.c` той же командой.

В файле `.asm` работают:

- комментарии — от `;`, `//` или `#` до конца строки;
- разделы — `.text` для кода, `.data` или `.bss` для данных (также `section .text`, `section .data`); файл начинается с `.text`;
- данные — `db`, `dw`, `dd`, `dq` с числами через запятую, `db` ещё и со строкой в кавычках (UTF-8, как в исходнике);
- `.align n` — выровнять следующее по `n` байт; `.zero n` или `resb n` — `n` нулевых байтов;
- `.local имя` — функция не попадёт в таблицу экспорта DLL, `.export имя` — попадёт (как `__declspec(dllexport)`, глава 10);
- `global`, `extern`, `bits`, `default` — принимаются ради совместимости с привычными ассемблерами и ничего не делают: в WinCC все имена и так видны всей программе.

Вот программа из двух файлов: счёт единичных битов по таблице и поиск старшего бита — в `.asm`, печать — в Си.

```
// файл: bits.asm
; Счёт битов по таблице и номер старшего бита
.data
nibble_bits:
    db 0, 1, 1, 2, 1, 2, 2, 3, 1, 2, 2, 3, 2, 3, 3, 4
hello_text:
    db "Привет из bits.asm", 0

.text
; int count_bits(unsigned long long v)
count_bits:
    xor eax, eax
    lea r8, [rip+nibble_bits]
.Lcb.next:
    test rcx, rcx
    jz .Lcb.done
    mov rdx, rcx
    and edx, 15
    movzx edx, byte ptr [r8+rdx]
    add eax, edx
    shr rcx, 4
    jmp .Lcb.next
.Lcb.done:
    ret

; int top_bit(unsigned long long v): номер старшей единицы, -1 для нуля
top_bit:
    mov eax, -1
    test rcx, rcx
    jz .Ltb.zero
    bsr rax, rcx
.Ltb.zero:
    ret

; const char *bits_hello(void)
bits_hello:
    lea rax, [rip+hello_text]
    ret
```

```
// файл: bitsmain.c
// сборка: wcc bitsmain.c bits.asm -o bits.exe
#include <stdio.h>

int count_bits(unsigned long long v);
int top_bit(unsigned long long v);
const char *bits_hello(void);

int main(void)
{
    unsigned long long values[] = { 0, 1, 255, 1000, 0x8000000000000001ULL };
    for (int i = 0; i < 5; i++)
        printf("%20llu: единиц %2d, старший бит %2d\n", values[i], count_bits(values[i]), top_bit(values[i]));
    puts(bits_hello());
    return 0;
}
```

```
                   0: единиц  0, старший бит -1
                   1: единиц  1, старший бит  0
                 255: единиц  8, старший бит  7
                1000: единиц  6, старший бит  9
 9223372036854775809: единиц  2, старший бит 63
Привет из bits.asm
```

Строка в `db` записана по-русски и печатается без всяких преобразований: в `.asm`, как и в `.c`, текст — UTF-8, а `puts` выводит UTF-8 в консоль правильно (глава 7). Команда `bsr` ищет старшую единицу, но при нуле результат не определён — поэтому ноль проверяется заранее.

## x87: 80-битные числа

У процессоров x86 два набора команд для дробных чисел. SSE — регистры `xmm0`…`xmm15`, числа в 4 и 8 байт; ими пользуется компилятор, и `double` считается ими. И старый сопроцессор x87 — стек из восьми регистров `st(0)`…`st(7)`, внутри которого числа хранятся в 80 битах: 64 бита мантиссы против 53 у `double`. В WinCC `long double` равен `double`, и x87 — единственный путь к повышенной точности. Он же даёт команды, которых нет в SSE: `fsin`, `fcos`, `fsincos`, `fptan`, `fpatan`, `fyl2x`, `f2xm1`, `fscale`, константы `fldpi`, `fldl2e`, `fldln2`.

Команды x87 работают со стеком: `fld` кладёт число наверх, `fstp` снимает его в память, арифметика берёт верхушку `st(0)` и следующие. Размер числа в памяти задаётся словом: `dword ptr` — `float`, `qword ptr` — `double`, `tbyte ptr` — 80-битное. Регистров `xmm` x87 не видит, поэтому дробный аргумент берётся из домашней ячейки, а ответ сначала кладётся в память и уже оттуда — в `xmm0`.

```
#include <stdio.h>
#include <math.h>

// Длина вектора на x87: все промежуточные числа — 80-битные
static double x87_hypot(double x, double y)
{
    asm("fld qword ptr [rbp+16]\n"      // st0 = x
        "fmul st, st(0)\n"              // x*x
        "fld qword ptr [rbp+24]\n"      // st0 = y, st1 = x*x
        "fmul st, st(0)\n"
        "faddp\n"                       // x*x + y*y
        "fsqrt\n"
        "fstp qword ptr [rbp+16]\n"     // результат — в ячейку первого аргумента
        "movsd xmm0, qword ptr [rbp+16]\n"
        "jmp .L.return.x87_hypot");
    return 0;
}

// Сумма ряда в 80 битах: отдельная ячейка в 10 байт держит накопленное
static unsigned char acc[10];

static unsigned short control;

// Windows держит x87 на 53 битах, как double; биты 8 и 9 слова управления — точность
static void acc_clear(void)
{
    asm("fnstcw word ptr [rip+control]\n"
        "or word ptr [rip+control], 0x300\n"    // 11 — полные 64 бита
        "fldcw word ptr [rip+control]\n"
        "fldz\n"
        "fstp tbyte ptr [rip+acc]");
}

static void acc_add(double v)
{
    asm("fld tbyte ptr [rip+acc]\n"
        "fadd qword ptr [rbp+16]\n"
        "fstp tbyte ptr [rip+acc]");
}

static double acc_get(void)
{
    asm("fld tbyte ptr [rip+acc]\n"
        "fstp qword ptr [rbp+16]\n"
        "movsd xmm0, qword ptr [rbp+16]\n"
        "jmp .L.return.acc_get");
    return 0;
}

int main(void)
{
    double big = 1e200;
    printf("hypot Си: %g, x87: %g\n", hypot(big, big), x87_hypot(big, big));
    printf("3-4-5: %g\n", x87_hypot(3, 4));

    double plain = 0;
    acc_clear();
    for (int i = 0; i < 10000000; i++) {
        plain += 0.1;
        acc_add(0.1);
    }
    printf("10 млн раз по 0.1: double %.10f, x87 %.10f\n", plain, acc_get());
    return 0;
}
```

```
hypot Си: 1.41421e+200, x87: 1.41421e+200
3-4-5: 5
10 млн раз по 0.1: double 999999.9998389754, x87 1000000.0000000871
```

Первая строка показывает, зачем бывают нужны 80 бит. `1e200` в квадрате — `1e400`, это больше наибольшего `double`; в обычной арифметике такое промежуточное число стало бы бесконечностью. Функция `hypot` из библиотеки обходит это хитростью, а x87 — просто тем, что его порядок вмещает числа до 10 в степени 4932. Третья строка — накопление ошибки: десять миллионов сложений по 0,1 в `double` ошиблись уже в четвёртом знаке после запятой, а в 80 битах — только в восьмом.

У третьей строки есть подвох, о котором стоит знать. Windows запускает программы с x87, урезанным до точности `double`: в слове управления сопроцессора биты 8 и 9 — точность, и Windows ставит в них 53 бита. Порядок остаётся 80-битным — поэтому первая строка работает и без настройки, — а мантисса округляется как у `double`, и без `fldcw` обе суммы совпали бы до последнего знака. Поэтому `acc_clear` сначала читает слово управления (`fnstcw`), ставит в нём оба бита точности и загружает обратно (`fldcw`). Настройка действует на весь поток до конца программы; код, который делает WinCC, считает дробные числа командами SSE и x87 не трогает, так что ему это не мешает.

! После вставки стек x87 должен остаться пустым: каждое `fld` — со своим `fstp` или `faddp`. Оставленное на стеке число переживёт функцию, и через восемь таких вызовов стек переполнится — дальше x87 молча выдаёт нечисла.

## Какие команды знает ассемблер

Ассемблер WinCC знает обычные команды x86-64 и x87 и, кроме них, наборы, которыми пользуются для быстрых вычислений: SSE до версии 4.2 и AVX с 256-битными регистрами.

Многоточие в таблице значит «все варианты этой команды»: `padd…` — это `paddb`, `paddw`, `paddd` и `paddq`.

Команды AVX работают с регистрами `ymm` по 32 байта — восемь `float` или четыре `double` за раз. Память такого размера называется `ymmword ptr`. Вот функция без пролога (о них — выше), которая складывает по восемь чисел из двух массивов; после работы с `ymm` принято ставить `vzeroupper`, чтобы следующие команды SSE не замедлялись:

```
// void add8(float *out, const float *a, const float *b): out[i] = a[i] + b[i], восемь штук
__declspec(naked) void add8(float *out, const float *a, const float *b)
{
    asm("vmovups ymm0, ymmword ptr [rdx]\n"
        "vaddps ymm0, ymm0, ymmword ptr [r8]\n"
        "vmovups ymmword ptr [rcx], ymm0\n"
        "vzeroupper\n"
        "ret");
}
```

Не у каждого процессора есть все эти наборы. Прежде чем пользоваться SSE4.2, AVX, `popcnt` или `rdrand`, стоит спросить процессор через `cpuid`, как в примере выше, — иначе на старой машине программа остановится с сигналом «неверная инструкция».

Ассемблер понимает и приставки сегментов `gs:` и `fs:`. В 64-разрядной Windows регистр `gs` указывает на блок сведений о текущем потоке (TEB), и `mov rax, qword ptr gs:[0x30]` кладёт в `rax` адрес самого этого блока. В `intrin.h` то же самое делают `__readgsqword` и `NtCurrentTeb`.

## Ошибки во вставках

На неизвестной команде сборка останавливается с файлом и строкой, как на любой ошибке Си. Во вставке `asm("…")` — и внутри функции, и вне функций — это файл и строка исходника на Си; в файле `.asm` — сам файл `.asm` и строка в нём:

```
bits.c:7: ассемблер: неизвестная команда bswp [bswp rax]
bits.asm:12: ассемблер: неизвестная команда bswp [bswp rax]
```

Саму строку с командой ассемблер повторяет в квадратных скобках, так что опечатку видно сразу. Окно WinCC показывает такую ошибку в списке ошибок с файлом и строкой, как и ошибку Си.

## Отладчик и стек вызовов

В каждой программе WinCC есть секция `.pdata` — сведения о том, как раскрутить стек каждой функции Си. Благодаря им отладчик (Visual Studio, WinDbg, x64dbg), остановившись внутри функции со вставкой — например, на `int3`, — показывает всю цепочку вызовов: кто вызвал эту функцию, кто вызвал того. Те же сведения нужны Windows, чтобы исключение прошло сквозь функции программы к своему обработчику. Сведения эти описывают кадр, который строит пролог, — ещё одна причина не трогать во вставке `rbp` и `rsp`.

## intrin.h: команды без вставок

Многие команды из таблицы нужны так часто, что Microsoft C давно даёт их в виде функций — их называют встроенными (intrinsics). В WinCC они собраны в заголовке `intrin.h`. Каждая из них — макрос с короткой вставкой внутри, поэтому вызов ничего не стоит: в программу встаёт сама команда процессора. Писать ассемблер, помнить про `@имя` и размеры операндов не нужно, а исходник собирается и у Microsoft.

```
#include <stdio.h>
#include <intrin.h>

int main(void)
{
    unsigned long long v = 1000;
    unsigned long top;
    printf("единиц: %d\n", (int)__popcnt64(v));
    if (_BitScanReverse64(&top, v))
        printf("старший бит: %lu\n", top);
    printf("байты наоборот: %llx\n", _byteswap_uint64(0x1122334455667788ULL));
    return 0;
}
```

```
единиц: 6
старший бит: 9
байты наоборот: 8877665544332211
```

Что там есть, по группам:

- процессор — `__cpuid`, `__cpuidex`, `__rdtsc`, `__rdtscp`, `_xgetbv`, `__debugbreak`, `_mm_pause`, `_mm_getcsr`, `_mm_setcsr`, `_ReturnAddress`, `_AddressOfReturnAddress`;
- барьеры памяти — `_mm_mfence`, `_mm_lfence`, `_mm_sfence`, `__faststorefence`, `_ReadWriteBarrier`;
- биты — `_BitScanForward`, `_BitScanReverse` (и с `64`), `__popcnt16`, `__popcnt`, `__popcnt64`, `__lzcnt…`, `_tzcnt_u32`, `_tzcnt_u64`, `_byteswap_ushort`, `_byteswap_ulong`, `_byteswap_uint64`, `_rotl`, `_rotr` и их варианты по размерам, `_bittest`, `_bittestandset`, `_bittestandreset`, `_bittestandcomplement`;
- длинная арифметика — `_umul128`, `_mul128`, `__umulh`, `__mulh`, `_addcarry_u64`, `_addcarry_u32`, `_subborrow_u64`, `__shiftleft128`, `__shiftright128`;
- память — `__stosb`, `__stosd`, `__stosq`, `__movsb`, `__movsq`;
- поток — `__readgsqword`, `__readgsdword`, `__readgsword`, `__readgsbyte`, `NtCurrentTeb`;
- атомарные операции — `_Interlocked…`, в том числе `And`, `Or`, `Xor`, для указателей и 16-битные.

Встроенных функций SSE с типом `__m128` в `intrin.h` нет — такие вычисления пишут вставкой, по таблице выше. Для атомарных операций между потоками есть и функции Windows: в `windows.h` — `InterlockedIncrement`, `InterlockedDecrement`, `InterlockedExchange`, `InterlockedExchangeAdd`, `InterlockedCompareExchange`, их 64-битные варианты с `64` на конце, `InterlockedAdd` и варианты для указателей; в программу попадают только вызванные.

## Итог

Вставка `asm("…")` вклеивает команды в ассемблерный текст функции как есть; единственное, что компилятор в ней меняет, — `@имя` локальной переменной или параметра, на место которого подставляется её ячейка в кадре. Так данные проходят во вставку и обратно без глобальных переменных и без счёта смещений. Аргументы функции лежат также в `[rbp+16]`, `[rbp+24]` и дальше по 8 байт, ответ можно оставить в `rax` или `xmm0` и выйти `jmp .L.return.имя`. Глобальные переменные доступны как `[rip+имя]`. `rbx`, `rsi`, `rdi`, `r12`–`r15` сохраняются, `rbp` и `rsp` не трогаются. Для переходов внутри вставки служат числовые метки `1:` с `1b` и `1f`. Функция с `__declspec(naked)`, `asm` вне функций и файлы `.asm` дают функции целиком, с аргументами в `rcx`, `rdx`, `r8`, `r9` и своим `ret`. Ассемблер знает команды битов, циклов, SSE до 4.2 и AVX с регистрами `ymm`; x87 открывает 80-битную арифметику, которой нет у `long double`. Ошибка показывает файл и строку — исходника на Си или файла `.asm`. А самые ходовые команды проще брать готовыми из `intrin.h`.
